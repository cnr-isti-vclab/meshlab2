USD Support¶

This document proposes reading and writing Pixar’s Universal Scene Description (.usda, .usdc, .usdz) in MeshLab, with its materials, and exporting a set of layers to one USD file. Stage 1, the flattened import and the one-layer export, is implemented (plugins/io_usd); stages 2 and 3 are not. Decided 2026-11-23 (Paolo): the library is LightUSD, and import starts flattened, as glTF’s does.

See also: Data Model (layers, materials, units), Project persistence (how saving works, and why a save is not a filter), Third-Party Code, Rendering (the material channels the renderer reads), plugins/io_gltf (the precedent for materials and for flattening a scene).

1. What USD asks of MeshLab¶

A USD file is a scene, not a mesh: a tree of prims with transforms, many meshes, instances, materials bound per face subset, cameras, and composition arcs (references, payloads, variants, sublayers) that assemble a stage from several files. Five properties matter for us:

  • Geometry is UsdGeomMesh with faceVertexCounts and faceVertexIndices: polygons of any size, not triangles. Attributes are primvars with an interpolation each: constant, uniform (per face), vertex, varying and faceVarying (per corner). Texture coordinates are usually primvars:st, faceVarying, with v up as in MeshLab and OBJ. A mesh can be leftHanded, which reverses the winding.

  • Materials are bound to a whole mesh, or to the faces of a UsdGeomSubset (family materialBind). The portable surface is UsdPreviewSurface, fed by UsdUVTexture nodes, each of which reads one or more channels of an image, with a scale and a bias.

  • Units and orientation are stage metadata: metersPerUnit, whose fallback by the specification is 0.01 (centimeters), and upAxis, whose fallback is Y. MeshLab keeps a file’s own frame (Data Model, “Frames are kept”); its default view is Y-up.

  • Packaging: .usdz is an uncompressed zip with the stage and its textures inside, the form Apple’s Quick Look, Blender, Omniverse and Houdini exchange.

  • Composition: a file can be a root layer that references others; what the user sees is the composed stage.

  • Read: the fixtures of section 7, and a few public USDZ assets (Apple’s AR Quick Look gallery, Pixar’s Kitchen Set), through Tydra’s render scene; check subsets, faceVarying texture coordinates, leftHanded, instancing and a referenced file.

Authoring is low-level. The writer builds prims with StageBuilder/LayerBuilder, values with Value::MakeFloatCompArray(..., TypeId::Point3f, 3) and the like, and records the USD type name of each property itself. A shader output (outputs:surface) is declared with add_property_slot on an interned name: a type name alone writes nothing, and the first attempt produced connections to undeclared outputs. The materialBind family must declare its type (subsetFamily:materialBind:familyType = "partition"): OpenUSD’s validator flagged its absence. The exporter is therefore some 300 lines of careful code, not a call. Both pitfalls belong in its comments and its round-trip test.

Verdict: go. Everything stage 1 needs works, at a cost in build time and size MeshLab already pays for comparable libraries.

Textures come from files beside the stage or from inside the .usdz; the latter load as in-memory assets with no file, as a .glb’s do, and Save Mesh to .usdz keeps them inside. UDIM paths (<UDIM>) are not supported in stage 1, and say so.

A known limit that stage 1 inherits. UsdUVTexture reads named channels: roughness is often the green channel of a packed image whose blue is metallic, as in glTF. The renderer read the roughness texture as the mean of its three channels, so a packed texture rendered wrong roughness from glTF; stage 3 added the channel (§6.1).

5. Stage 2: scenes¶

5.1 The interface¶

A plugin returns one mesh. A scene needs the layers, each with its matrix, label, visibility and material set. The proposal is the smallest addition that carries that: two optional calls on MeshIOPlugin, loadScene and saveScene, taking a list of layer views (mesh, matrix, label, visible, material set and texture context), and a capability flag. Document drives them as it drives load and save. glTF can implement them later; nothing else changes. This is new framework code and needs approval before it is written.

5.2 Export Visible Layers as USD¶

A document operation beside Save Project, not a filter: saving changes the disk, not the document, by the project-persistence rules. One self-contained file, .usdz to send, .usdc or .usda to work with.

The .mlp stays MeshLab’s project. A second form, a root file referencing one USD file per layer (what a .mlp does), is possible and not proposed: it would be a second project format to keep in step.

5.3 Import as Separate Layers¶

The other half: each UsdGeomMesh, UsdGeomPoints and UsdGeomBasisCurves prim becomes a layer, its world transform the layer matrix and its prim name (or displayName) the label. A file written by 5.2 then comes back as the layers that wrote it. A menu entry beside Import Mesh; plain Open keeps flattening.

Cameras are left out of stage 2 (decided 2026-11-28), both ways: a camera with no image is not a raster, and the place for it is the annotations framework to come, which will attach geometric information of several kinds to layers.

Where an imported layer comes from is an open problem (recorded 2026-11-28). For now a layer imported from a scene has no file of its own: it is not reloadable, and Save asks for a new file. A layer could instead record the scene file and its prim (as package.usdz[entry] names a texture inside a package), so that Reload reads that prim again and the stored-state mark knows the layer still holds it; that needs provenance below the file level in MeshEntry, in the stored-state record and in the project, and is worth doing once more than one format imports scenes.

5.5 As implemented (2026-11-28)¶

Interface (src/plugins/meshioplugin.h): holdsScenes(filename), loadScene(filename, layers, cb, context) filling MeshIOSceneLayers (mesh, load mask, material set, matrix, label, visibility), and saveScene(filename, views, options, cb) taking MeshIOSceneLayerViews (mesh, mask, matrix, label, texture context). Document: importLayers(filename, error, options) and exportVisibleLayers(filename, error), File > Import Layers… and File > Export Visible Layers… (offered for the formats whose plugin holds scenes), Python ms.import_layers(path, **options) and ms.export_visible_layers(path). An import is one undo step, recorded as import_layers with its load options; an export changes no layer and no layer’s file.

Import. Each Mesh, Points and BasisCurves prim is a layer in the prim’s own coordinates; its world transform is the layer matrix, its displayName (or name) the label; an invisible prim is a hidden layer. Curves come from Tydra’s tessellation, one polyline per curve, its vertices shared; a polyline whose last point repeats its first closes on it. The rotateYUpToZUp option turns a Y-up stage by a rotation in front of every layer matrix, the coordinates untouched. Plain Open flattens as before, now with curve prims as edges too.

Export. Each visible layer is a prim under /World, named from its label and unique, with the label as displayName and the matrix as xformOp:transform, not baked. A layer with faces is a Mesh, without a Points; its edges are linear BasisCurves beside it (alone for a polyline), one curve per chain of Clean::EdgeMeshChains, so a polyline’s vertices stay shared when read back. Materials of every layer go under /World/Looks; a texture file or image used by several layers is written once. A one-layer Save goes through the same writer, without a transform or displayName, and now writes edges too (stage 1 dropped them).

Shared with load and save (the table approved before the move): Document::prepareImportedMesh and logImportedMesh are the post-import steps of loadMesh, reloadMesh and importLayers (reload used to skip registering the PBR channel textures, so a reloaded layer lost its normal, occlusion and roughness maps); texturesToSave and maskToSave the save preparation of saveMesh and exportVisibleLayers; Document::CallbackScope the progress-callback setup each of them repeated.

Not done: cameras (5.3); provenance of an imported layer (5.3); per-layer up axis (a Z-up stage read as it is comes back declared Y-up); a branching polyline (a vertex of degree 3 or more) comes back with that vertex once per chain; the mirrored-matrix winding that the flattened import reverses is left to the layer matrix.

Measured: usdScenesRoundTripVisibleLayers (usda, usdc, usdz: three visible layers and a hidden one; labels, matrices, local coordinates, a polyline and a closed loop back, one undo step, the flattened Open placing each prim, a polyline saved alone keeping its edges); reloadKeepsMaterialChannelTextures.

6. Stage 3: the material model (data only)¶

Scope, decided 2026-11-28. Stage 3 is about what MeshLab keeps: every material input that glTF and USD share is read, kept on the layer and written back by both, so that neither format loses material data on a round trip. It draws nothing new. The view’s PBR material mode is not physically based today – Blinn-Phong, roughness choosing the highlight’s exponent and strength, a constant ambient, no Fresnel and no environment lighting (shaders/fill_smooth.frag:150-185) – and metallic and transparency only mean something under a real metallic-roughness shading with image-based lighting. That is a rendering proposal of its own; it will also decide what the current mode becomes. The Plain material mode reads none of these fields.

glTF 2.0 (core metallic-roughness model) and USD’s UsdPreviewSurface share one set of inputs: base color, metallic, roughness, normal, occlusion, emissive, opacity with a cutoff. They differ in that glTF packs roughness and metallic into the green and blue of one image where USD connects each channel by name, and in what each adds beyond them (USD: specular workflow, clearcoat, ior; glTF: extensions). One slot model carries both.

Measured 2026-11-28 (every read and write of MeshIOMaterialSlot, with the evidence below): the glTF importer indexes its slots by material and its faces’ texture index by base-color image, while every consumer reads the face index as the slot; the renderer reads a roughness texture as the mean of its channels; the glTF exporter writes the base color only, and tinygltf’s omitted defaults make every exported material fully metallic; USD reads and writes neither normal scale nor occlusion strength; undo copies the material set whole, and .mlp stores no material.

6.1 As implemented (2026-11-28)¶

MeshIOMaterialSlot gained metallicTexture, emissiveTexture, baseColorFactor (RGBA, the alpha the opacity), metallicFactor (0 unless a file says otherwise), emissiveFactor, alphaMode and alphaCutoff; MeshIOMaterialTextureRef gained channel (RGB, R, G, B, A); forEachTextureRef(slot, f) walks all six references, and every former hand-written walk uses it (reference normalization, texture registration on load, the load log, texture removal, the layer widget’s list, which now tags Metal and Emissive).

  • glTF import (row 0): one slot per material whose base color texture could be read, each face’s texture index its material’s slot, a material with no base color texture giving its faces its base color factor and slot -1. Base color assets sit at their slot’s index, channel images after, once each. Every input is read: roughness green and metallic blue of the metallic-roughness image, occlusion red, emissive, the factors (tinygltf supplies the specification’s defaults), alpha mode and cutoff. A textured material’s base color factor is kept in the slot and no longer baked into vertex colors.

  • glTF export (row 3): one material per slot the faces use, written whole, each image once; the metallic-roughness image is the slot’s own when roughness and metallic name it in green and blue (or there is no metallic map and the factor is 0), else packed from the two maps; a single-channel map in another channel than glTF’s is repacked; factors are written always, so a slot with no metallic of its own no longer reads as fully metallic.

  • USD (row 2): channels from the connected UsdUVTexture output, both ways; each texture’s scale carries the factor that multiplies it (base color, roughness, metallic, emissive), the normal scale as scale and bias; opacity is the base texture’s alpha (or a value), a threshold a mask. The converter makes one texture per connected output, so the base color and its alpha are matched by prim, not by texture id. USD has no occlusion strength: a strength other than 1 is not written (a save has no channel to the log, so this is said in the code only). ior and displacement are now noted as dropped; metallic, emissiveColor and an opacity read from the base texture no longer are.

  • Drawn (row 1): the roughness texture’s channel reaches the fill shaders in the roughness flag (mode + 4 × channel), so the uniform block’s layout is unchanged; a glTF roughness is read from green, no longer from the mean of three channels. Nothing else new is drawn.

  • Row 0b dropped: with untextured materials kept as colors (question 5), no slot is ever without a base color texture, so the GPU cache needs no change for it.

  • Cleanups: the GPU cache’s two batch-filling blocks are one (takeGroupMaterial), and the memory accounting no longer walks the material set’s assets, which only travel in from an importer (the field’s comment now says so).

Measured: gltfFacesUseTheirOwnMaterial (fixture tests/data/gltf/shared_materials.gltf); materialsRoundTripThroughGltfAndUsd (every field through .glb and .usda, the packed image’s channels, a red roughness map repacked to green). Not measured: the draw of the roughness channel, which only a render probe sees.

Left to the rendering proposal: drawing the base color factor, metallic, emissive and alpha; sRGB decoding of base color and emissive (every image is uploaded as plain RGBA8, meshgpuresourcecache.cpp:566-568); the global PBR values written to the uniform block and always overwritten (renderwidget_internal.h:403-448). A separate fix: six texture filters rebuild a layer’s slots from base colors only, dropping its normal, occlusion and roughness maps and its factors (replaceTextureAssociations, textureassociationutils.cpp:359-375).

7. Validation¶

  • Fixtures written by us, small .usda files committed under tests/data/usd/: a quad and two triangles with faceVarying coordinates and two materials by subsets; a leftHanded mesh on a Y-up stage with no unit and an invisible prim; a referenced mesh, once translated and once as a mirrored instance. Ours, so no licence question; public assets only in the local dataset, by test_data.md.

  • Round trips in tests/test_document.cpp, beside the glTF ones: save a layer, load it back, compare positions, coordinates, slot indices and the four material channels.

  • OpenUSD as a checker: when usdchecker (pip usd-core) is on the path, every file the tests write must pass it; skipped otherwise, as the datasets are.

  • By hand, once per stage: the .usdz opens in Quick Look and in Blender.

8. Cost¶

io_gltf is about 2,000 lines; io_usd is expected to be similar, plus about 150 for the scene interface of stage 2 and the two document operations. Stage 3 is a change across five places whose size its mapping table will tell.

9. Open questions¶

  1. ~~Up axis.~~ Settled 2026-11-28: MeshLab keeps a file’s own frame, for every format. A rotation is the user’s choice, the rotateYUpToZUp load option of USD and glTF, off by default and logged (Data Model, “Frames are kept”).

  2. Unit fallback. A stage that does not author metersPerUnit is in centimeters by the specification. Report centimeters (by definition, as glTF’s meters), or Unknown (as for a format that does not say)? Stage 0 showed the importer can tell the two apart (metersPerUnit_set); Tydra’s own fallback, 1.0, is used by neither choice. Stage 1 reports centimeters.

  3. ~~Scene interface (5.1).~~ Approved 2026-11-28: holdsScenes, loadScene, saveScene. Cameras are left to the annotations framework, and imported layers have no file of their own for now (5.3).

  4. Stage 3 timing: right after stage 1, or after stage 2?

  5. Untextured materials (stage 3, row 4). Kept as today – face or vertex colors, so that the renderer’s grouping by texture is unchanged, and their metallic, emissive and alpha are lost on a round trip – or slots of their own carrying only factors, which keeps the material but makes every material a draw group?
