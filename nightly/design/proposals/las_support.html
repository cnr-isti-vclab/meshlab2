LAS/LAZ Support¶

This document proposes reading and writing ASPRS LAS point clouds and their compressed form, LAZ, in MeshLab. It also proposes the piece any georeferenced format needs and MeshLab lacks: a document origin, so that coordinates in the millions keep their precision. Nothing described here is implemented.

See also: Load Options (how the user chooses what to read), Data Model (layers, units, provenance), Memory Accounting, Third-Party Code, plugins/io_e57 (the other point-cloud format, and the one that measured the problem).

1. What LAS is¶

The ASPRS LAS format (1.0 to 1.4) holds one point cloud and no faces. A header gives the bounds, point count, scale and offset: each coordinate is a 32-bit integer X, and the position is X * scale + offset in double precision. Point records come in formats 0 to 10:

  • every format has intensity, return number and count, classification, scan angle, user data and point source ID;

  • GPS time from format 1 on, RGB (16 bits per channel) in 2, 3, 5, 7, 8 and 10, near-infrared in 8 and 10, and waveform packets in 4, 5, 9 and 10;

  • from 1.4 on, extra per-point fields of any type (“extra bytes”, declared in a VLR). PDAL and others write normals there as NormalX/NormalY/NormalZ.

The coordinate system is a variable-length record (WKT in 1.4, GeoTIFF keys before), whose linear unit is usually the meter and sometimes the US survey foot. LAZ is the same content compressed losslessly by LASzip. COPC (cloud-optimized point cloud) is a LAZ 1.4 file whose points are ordered in an octree described by an extra VLR. Any LAZ reader reads it whole.

2. The real problem: precision¶

VCGVertex stores positions in float (vcg::vertex::Coord3f, src/core/vcgmesh.h), and the layer matrix is a float QMatrix4x4 (Document::meshTransform). A float has a 24-bit mantissa. At a UTM northing of 5,000,000 m it can only store multiples of 0.5 m, and at an easting of 500,000 m multiples of 3 cm. Most LAS files are in such coordinates. Moving the offset into the layer matrix does not help, because the matrix is float too.

Measured on E57, which MeshLab already reads, 2026-11-25. A 100 × 100 grid with 1 mm spacing was written as doubles with libE57Format and read back through load_new_mesh:

The 10,000 points come back as 4 columns and 1 row: the survey is gone. The importer converts each point to float after applying the scan pose (vcg::Point3f::Construct(rotation.Rotate(p) + translation), plugins/io_e57/e57importplugin.cpp) and subtracts no offset, so a scan placed by its pose loses precision exactly as one stored in absolute coordinates does.

The proposal: a document origin. Document gets an origin, a vcg::Point3d kept in double precision; every layer’s coordinates are relative to it.

  • On load, the importer subtracts the origin in double precision, before converting to float. This changes the importer, not Document: once the values are float the precision is already lost. The origin is one more input to MeshIOPlugin::load, the second after load options, which tips Load Options §6.1 toward a request struct.

  • Which origin. If the document has one, every new layer uses it, so layers still align. If it has none and the file’s coordinates are far from zero, the file proposes one and the document adopts it. “Far” means the bounding box centre is farther from zero than its diagonal is long. The proposed origin is the file’s own LAS offset, or the bounding box minimum rounded to whole units. A file near zero sets none, so everyday meshes are unaffected.

  • On save, formats that store doubles and are georeferenced by nature (LAS, E57) add the origin back, so a load and save round trip keeps the true coordinates. The others write local coordinates and log the origin (open question 2).

  • Shown wherever a position is shown to the user: the measuring and picking tools add the origin when it is set, and the status bar says it is in effect.

  • Kept in the project as <Origin x="..." y="..." z="..."/>, a sibling of <LengthUnit>, which legacy MeshLab skips. File > New clears it. It is not part of the undo state, because nothing but a load sets it: like the unit, it is adopted, never edited by a filter.

  • Python: ms.document_origin().

The fix is a few dozen lines in Document and the project reader and writer, and a few lines in each importer of a format that can be georeferenced: E57 now, then LAS, then glTF/USD if ever needed (both are usually local). E57 goes first, with its measured test as the regression test.

LASzip. It is a small library that reads and writes both plain LAS and LAZ through one API, which is all an importer needs. PDAL is a pipeline framework, and its dependency chain is far heavier than one file format justifies. The coordinate-system VLR is kept as text (WKT) for the round trip, so no PROJ is needed: MeshLab does not reproject.

Expression filters already read named per-vertex int, float and Point3f attributes (plugins/filter_expression/expressionfilterplugin.cpp). Before relying on them, check that named attributes survive undo snapshots and tri::Append.

Size. One airborne tile is often 10 to 100 million points, a mobile or terrestrial survey more. A vertex takes about 40 bytes before named attributes, so 100 million points is about 4 GB. The default load is therefore not “everything” but at most a point budget, 30 million points to start, by an even stride. The stride keeps the scan pattern and needs no second pass. Above the budget the log says how many points were skipped; Reload with Options… on the layer loads them all (Load Options). A spatially even subset is a filter’s job once the points are in.

The point format is the smallest that holds what is written: 6 without color, 7 with it, 8 with near-infrared. This means LAS 1.4, which old readers do not open (open question 1).

6. COPC (stage 4)¶

A COPC file stores its points in octree order, and its hierarchy VLR gives the point range of each node. Reading a level of detail, or the nodes inside a box, is then a seek and a read per node, through LASzip’s seek. That turns the point budget of §4 from a stride into a spatially even subset, and lets a region of a national survey be opened without reading the rest. It is a few hundred lines of hierarchy parsing, worth doing once stage 2 is in use.

7. Validation¶

  • Fixtures in tests/sample_mesh/las/: small LAS and LAZ files in formats 1, 3, 6, 7 and 8, one with extra bytes and one with RGB stored in 8 bits. Synthetic ones are generated with LASzip; one real airborne tile goes in the dataset manifest, not the repository (Test Data).

  • tests/test_document.cpp: a georeferenced round trip (load, save, load) that keeps every point within half the file’s scale, run on LAS and on E57; the E57 grid above as the regression test of stage 1.

  • Descriptor and smoke tiers are unaffected, as for any importer.

9. Open questions¶

  1. LAS 1.4 or 1.2 on export. 1.4 holds 8-bit classification, extra bytes and the WKT, but some older tools refuse it. Should 1.4 be written always, or 1.2 when nothing needs 1.4?

  2. Origin on non-georeferenced formats. Should PLY, OBJ and STL write true coordinates, losing precision in float formats, or local ones plus a log line? A save option, or never?

  3. GPS time. Kept by default, offset by its minimum, or dropped unless asked for? It is 8 bytes a point in double and useless to most users.

  4. The point budget. Is 30 million points right, and should it follow the memory preferences rather than be fixed?
