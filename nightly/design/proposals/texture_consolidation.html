Texture Consolidation¶

Status: proposal, not implemented (2026-10-28). Integrating Liu, Wang, Kim and Kazhdan, Texture Consolidation of Generated Multi-View Renderings (arXiv 2610.36098, 2026) — code at hliuw/TextureConsolidation — as a second implementation of Transfer Color from Visible Rasters to Texture.

Everything under Upstream, measured was read from the repository and its three dependencies on 2026-10-28, not inferred from the paper or the README.

What it does¶

Given a texture-atlased triangle mesh and a few images with known cameras, it produces one seamless texture image. Three steps:

  1. Back-projection with confidence. Each image is projected into texture space, giving a color texture and a confidence texture per view. Confidence is the product of a normal term (clamped dot product of normal and view direction) and a depth term that falls off near depth discontinuities of the mesh as seen from that camera, so texels near silhouettes — where a generated image and the geometry disagree most — count less. Colors are then normalized by a local mean and scale, which the paper finds essential for the optical flow to be stable.

  2. Registration by optical flow on the surface. A flow field per view, at mesh resolution, aligning that view’s colors to a target built incrementally from the views already registered; hierarchical, coarse to fine. This is what removes ghosting.

  3. Gradient-domain stitching in texture space (Prada, Kazhdan, Chuang, Hoppe 2018), confidence-weighted, which removes the remaining seams and color steps.

It was designed for generated renderings, which are geometrically inconsistent with the mesh and with each other, but works on real photographs: the paper shows two RGB-D scans, and the repository’s own example is nine photographs of a vase that are, according to its README, courtesy of Paolo Cignoni and Marco Callieri.

How it will differ from the incumbent. Transfer Color from Visible Rasters to Texture (filter_color_projection) blends the projected rasters with angle, distance, border, silhouette and alpha weights. It does not move any color. This method moves colors along the surface to register the views before blending, and stitches in the gradient domain afterwards. Expect it to remove ghosting and seams that blending keeps, at the cost of runtime (the paper reports 71–83 s for 9–16 views at 1024², and 842 s and 1725 s for 33 and 55 views) and of the method’s own failure cases: drift where the views overlap little, and twisting on repeated patterns whose count differs between views (paper Figs. 13, 15).

Input and output are files. A binary PLY with vertex_indices and a per-face texcoord list of six values; a cameras.json of OpenCV-convention pinhole cameras (w, h, fx, fy, cx, cy in pixels, and a 4×4 world-to-camera w2c); one PNG per camera. The output is a single PNG texture.

Errors: two of the three programs report them correctly; the stitcher does not always. Misha’s MK_ERROR_OUT prints a message and calls exit(0) (Misha/Exceptions.h, lines 107 and 148), and the macro is #ifndef-guarded. BackProjection and TextureFlow both define it to MK_THROW before including Misha, catch in main, print [ERROR] … and return EXIT_FAILURE. TextureDomainStitching is TextureSignalProcessing’s TextureStitching.cpp, built unmodified: it also catches and returns EXIT_FAILURE, but it does not redefine the macro. Its MK_ERROR_OUT paths still exit with status 0, so they look like success. Three are in TextureSignalProcessing: “Bad component” (singular, Src/SimpleTriangleMesh.inl:152), “Expected covering triangle” (a sanity check, HierarchyConstruction.inl:222) and an index-size check (MultiIndex.h:216). The rest are whichever of Misha’s 36 files’ calls the stitcher reaches. The README’s “Bad components” (plural, line 161) is an MK_THROW, and fails correctly.

Progress is already reported. With --verbose, BackProjection prints at the end of each stage. TextureFlow prints Level l: target …, error … -> … for every hierarchy level, which is where the time goes. Those lines are usable as the runner’s stage markers as they stand.

OpenMP is required by the build, not by the code. Every parallel loop in the three programs goes through Misha’s ThreadPool::ParallelFor. Its backend is the first entry of an enum that lists OpenMP only #ifdef _OPENMP, and std::thread (ASYNC) otherwise. Only the find_package(OpenMP REQUIRED) in TextureConsolidation’s CMakeLists.txt makes it mandatory.

No symbol clash with the vendored PoissonRecon. Misha is in namespace MishaK, PoissonRecon 18.75 in plugins/filter_screened_poisson/Src in namespace PoissonRecon. But 41 headers share a file name and include guard with it (Geometry.h, Array.h, PlyFile.h, SparseMatrix.h, …), so the two must never share an include path.

Route: unmodified submodule, run as helper processes¶

Three routes were considered.

Route

For

Against

A. Pinned submodule; build the three programs unmodified; run them as helpers

Zero patches. An exit(0), an assertion or a crash ends a child process, not MeshLab. Exactly the QuadWild-BiMDF arrangement, whose runner (src/core/helperprocess.{h,cpp}) already gives progress, cancellation and logging. C++20 and OpenMP stay inside the helper build.

Packaging on three platforms. File I/O round trip, small beside a minute-long solve.

B. Link the headers into the plugin

No files, no packaging

The stitcher is a program (TextureStitching.cpp with its own main), not a library; using it in-process means vendoring it with patches. Every MK_ERROR_OUT path would have to be redirected — the macro is #ifndef-guarded, so predefining it to throw is possible, but unverified against assertions and other exits. OpenMP and C++20 enter the application build.

C. Vendor a subset under upstream/

Freezes a moving target

It would be a patched copy of a repository three weeks old and changing daily.

Recommended: A. Under the third-party rule it is the “no change, no suitable port” case: a pinned, unmodified submodule. No vcpkg port exists for any of the four repositories. Route B would turn that into “we patch it”, which means vendoring, for a gain that is not needed.

The pin should be advanced deliberately rather than tracked. Whether the authors will keep the command-line interface stable is a question for them (see Open questions).

What the adapter does¶

  1. Check, then refuse with a message, before anything runs. At least one visible raster. Every raster is perspective (CameraType 0) with zero lens distortion, because cameras.json has no distortion terms; an undistortion step can come later. The mesh has an atlas. The mesh is connected, as the README requires; whether one connected component is the whole condition is open question 4.

  2. Export to a temporary directory. The mesh as binary PLY with per-wedge texcoords, with the layer matrix applied, since the cameras are in world space. One PNG per visible raster from its RGBA plane. cameras.json from each CameraShot.

  3. Run the three helpers in turn through HelperProcess::run, each with its own share of the progress bar, and with cancellation honoured between and during them.

  4. Do not trust the stitcher’s exit code alone. Its MK_ERROR_OUT paths can report success, so until change 1 below lands, a step succeeds only if its expected output files exist and decode at the expected size, and no [ERROR] line appeared on its output. Anything else fails the filter with the helper’s last message, and the temporary directory is kept and named in the log. The output check is worth keeping afterwards too; it is cheap.

  5. Attach the result as a new texture of the layer. The UVs are not touched.

Camera conversion, the part that must be tested rather than reasoned¶

CameraShot holds the intrinsics in millimetres: FocalMm, PixelSizeMm, CenterPx, ViewportPx. The pinhole terms follow as fx = FocalMm / PixelSizeMm.x, fy = FocalMm / PixelSizeMm.y, with w, h from ViewportPx. On the gargoyle fixture that is 750 × 502 pixels with focal lengths from about 1,630 to 2,490 px. The rest is convention, and conventions differ in exactly the ways that still produce a plausible texture: vcglib’s camera looks down its own axis and its image origin may sit at the bottom, while OpenCV looks down +z with y pointing down and the origin top-left. So cy, the axis flips in w2c and the row order of the written PNGs are settled by a test, not by derivation. Project every vertex of a mesh through vcg::Shot and through the converted pinhole model, and require the two to agree to well under a pixel. A wrong sign here does not crash anything. It shifts every projection, as a wrong intrinsic did on the raster fixture before (see AGENTS.md).

Tests¶

  • Descriptor tier: automatic. The rules on textureoutputref, the categories and the name grammar apply unchanged.

  • Smoke tier: no fixture rung has both an atlas and rasters (the rasters rung is the gargoyle without UVs, and the parametrized rung has no rasters), so the filter refuses with a message on every rung. It goes into expectedRefusals() with that reason, which keeps the slow solve out of the smoke sweep.

  • Behavioural:

    • The camera conversion test above. Fast, no helpers needed.

    • End to end on the gargoyle fixture, atlased with xatlas first, at a small texture size: a texture is produced, attached, of the requested size, covering the atlas charts that the rasters see.

    • Against the incumbent on the same input, using Measure Texture Seam Color Discrepancy: consolidation should leave smaller seam discrepancies. That is the claim the method makes, and a measurement the repository already has. The paper’s own image metrics (LPIPS, SSIM, ECD) do not all favour it, and it says why (App. C), so the assertion should not use them.

    • Failure path: a disconnected mesh is refused before any helper runs.

  • Dataset: the vase from the upstream release (example-data/vase.zip) — your and Callieri’s data, by the README — is texture_consolidation_vase in tests/datasets/datasets.json, with its sha256 and size. Its licence is UNRESOLVED and it is not CI-eligible until you settle that; no test uses it yet.

Packaging¶

  • Submodule external/texture-consolidation, recursive (its three submodules come with it), registered and pointing at the fork while its changes are proposed upstream.

  • Helper build through ExternalProject_Add, as QuadWild does, targeting the three programs and passing our toolchain, so that its find_package calls find vcpkg’s libraries.

  • vcpkg gains libpng and libjpeg-turbo; zlib is already installed.

  • OpenMP is REQUIRED upstream and stays so (change 2 below was not pursued). A missing OpenMP inside an ExternalProject fails the whole build at build time, so on macOS the plugin looks for a runtime at configure time with the hints filter_screened_poisson uses (OpenMP_ROOT, then Homebrew’s libomp) and skips itself with a message when there is none; GCC and MSVC bring their own. On macOS the helpers then need a libomp at run time: whether the one the application already ships is reachable from Contents/Helpers is to be verified.

  • Bundling: meshlab2_bundle_quadwild is QuadWild-specific, and the three release workflows (AppImage, Windows portable, macOS DMG) have QuadWild-specific steps. With a second helper package the bundling function should become a general one taking a name, executables and resources, rather than being copied. That is a small refactor, with its own mapping table when it happens.

Phases¶

Phase 0 — feasibility, no MeshLab code (about a day). Add the submodule (done: it points at the fork). Then build the three programs with our vcpkg on macOS. Run the upstream vase example and time it. Hand-export the gargoyle, atlased by xatlas, to their format with a throwaway script, and run it end to end. Read the helpers’ output to find stage markers for the progress bar, and confirm that nothing in the pipeline is random. Exit: both datasets produce a texture, and the runtime is known.

Phase 1 — the adapter (two to three days): camera conversion and its projection test, the plugin and descriptor, the checks, the error detection, attaching the texture, and the tests above.

Phase 2 — packaging (one to two days): the general bundling function, the three workflows, libomp on macOS, the About entry, UPSTREAM.md, and the external/README.md paragraph saying why it is a submodule and not a port.

Possibly later: the paper’s drift mitigation (registering to a stationary coarse texture, Fig. 15b), if the programs expose it — the README lists no such option; and lens undistortion, so that distorted rasters can be used instead of refused.

Status, 2026-10-29 (Phase 1 done; Phase 2 not started)¶

Phase 0. The authors’ vase example (texture_consolidation_vase in tests/datasets/datasets.json, licence unresolved, not used in CI) runs end to end through the three programs: 27.5 s with OpenMP, 28.4 s without. Building without OpenMP exposed a crash in Misha’s std::thread ParallelFor, whose futures were a static local shared between concurrent calls. A fix was written but is not committed anywhere: the helpers build with OpenMP, which does not reach that code.

Phase 1. plugins/filter_texture_consolidation provides Transfer Color from Visible Rasters to Texture (Texture Consolidation). It builds the three helpers through ExternalProject with vcpkg’s libpng and libjpeg-turbo, and finds them in the build tree. What it does:

  • refuses: no atlas; fewer than two visible rasters; non-perspective or distorted cameras; an atlas of about one chart per face (facesPerChart < 2). The last was found by the smoke tier’s raster rung, whose 20,000 one-triangle charts held the stitcher for minutes at 9–12 GB. A real xatlas atlas of the same mesh has 300 charts, and the vase 65;

  • scales the mesh and cameras to surface area 5, the scale the vase data was prepared at, and converts each vcg::Shot to an OpenCV pinhole camera (pinholecamera.h);

  • checks every helper’s outputs, keeps the intermediate files on failure (and on request with MESHLAB2_TEXTURE_CONSOLIDATION_KEEP), and turns the stitcher’s “Failed to factorize matrix” into advice to raise the texture size: on the gargoyle, 256² usually fails, 512² works with warnings, and 1024² is clean.

Tests, all on the gargoyle raster fixture:

  • textureConsolidationCameraMatchesShotProjection: the conversion agrees with Shot::Project on every visible vertex within 0.05 px, gives the same pixel index as MeshLab’s raster sampling, and is unchanged by world scale;

  • textureConsolidationBuildsTextureFromRasters: xatlas atlas, then 1024² at 3 levels; a 1024×1024 texture is attached and covers more than 20% of it (29.4% is typical). The helpers are not deterministic (finding 1), so nothing is compared against a reference image. Also asserts the refusals for no atlas and for fewer than two rasters;

  • the smoke tier lists the filter in expectedRefusals(): no rung has both a real atlas and rasters.

The About box and the third-party test list TextureConsolidation, and the third-party test classifies libpng and libjpeg-turbo.

Builds. On macOS the plugin needs an OpenMP runtime (OpenMP_ROOT, or Homebrew’s libomp) and skips itself without one. Windows (MSVC) builds all three helpers in CI, but that workflow does not run ctest. On Linux the helpers need GCC 13, so the AppImage moved from Ubuntu 22.04 to 24.04 (see release_process.md); the first 24.04 run is in progress at the time of writing.

Compile cost. The stitcher is one translation unit and dominates the build: 2.5 min and 4.4 GB with Apple clang, 7.4 min and 4.7 GB with GCC 16 on the same machine, about 8 min with MSVC in CI, against seconds for the other two programs. It is not the source size: all three preprocess to 205,000–240,000 lines, but the stitcher’s object file is 32.7 MB against 0.8 and 2.1 MB. -O0 takes 17.5 s, so nearly all of it is optimization of template copies. Precision (2 values, TextureStitching.cpp:1518) and texture bit depth (4 values, :1437) are run-time options dispatched to template parameters, so the whole Stitching class is compiled 8 times; inside each copy, the operator assembly is built for 6 quadrature values (Operators.inl:1376), 2 sanity-check settings and 4 call sites with their own lambda types (TextureStitching.cpp:777–786). About 384 copies, of which a MeshLab run (float, 8-bit, quadrature 6) executes one.

Found in upstream behaviour, for the authors:

  1. Not deterministic, under OpenMP too. On identical inputs, BackProjection differs from run to run in about 10 texels per megapixel, by up to 158/255. TextureFlow differs in up to 4% of texels, about 0.1% by more than 10/255. The stitcher alone is deterministic.

  2. TextureFlow could loop forever. When every remaining overlap is NaN, the source-selection if( overlap>maxOverlap ) never fires and while( true ) re-solves one view indefinitely. It hung in about 1 run in 8 on the gargoyle. Now a reported error, in fork commit 4efb2e6.

  3. The advection produces non-finite values in roughly 1 run in 5 or 6 on the gargoyle (15 of 80, then 13 of 80 with the advection loop made serial), anywhere from 1 to 2,765 texels. It is not a race in that loop. Most such runs used to finish “successfully”, carrying NaN-derived texels, which is the likely cause of one run’s 95.8% coverage against the usual 29.4%. Whether a non-finite advected sample should be treated as zero confidence, or reported, is the authors’ call.

  4. The stitcher’s compile cost (above). The bit depth looks to matter only for reading and writing images, though that is not verified; if so, making it a plain run-time value would cut the stitcher’s compile time about fourfold. That would be a pull request to TextureSignalProcessing, not to TextureConsolidation.

Repeatability fixes, 2026-10-29¶

The nondeterminism reported above was reproduced on the vase with the Release build, 512² textures and three flow levels. Two parallel runs differed already in every back-projected image; one flow run failed with non-finite overlap. Limiting OpenMP to one thread made back-projection repeatable, but the flow still differed. Initializing the advection output alone made two serial pipelines byte-identical, including all intermediate PNGs. This distinguishes an uninitialized-read bug from scheduling effects.

The fixes belong to the helpers and their upstream libraries, not to MeshLab’s adapter:

  • TextureConsolidation, TextureAdvection.inl: zero-initialize the output before writing supported atlas texels. RegularGrid<double> allocates uninitialized scalar storage; confidence outside the atlas was subsequently read by interpolation and erosion. Point-valued color grids already default to zero.

  • TextureConsolidation, BackProjection.inl: sum depth-Laplacian variance in pixel order. Atomic floating-point addition prevented data races but did not fix rounding order. Computing the Laplacian and confidence remains parallel.

  • Misha, Texels.inl: when candidate simplices have exactly equal squared distance, choose the lowest simplex index. Candidate lists are assembled by worker, so their order is not stable. This matches the first candidate of a serial simplex traversal.

  • PhongRodriguesVF, SimplicialMeshProcessing.phong.inl: build tangent frames by projecting coordinate axes and choosing the largest residual, breaking ties in axis order. The previous random tangent basis consumed shared rand() calls inside a parallel loop. The new basis spans the same tangent plane without random sampling.

  • PhongRodriguesVF, SimplicialMeshProcessing.integration.inl: evaluate element matrices in parallel, then accumulate them in simplex order, following the existing vector-assembly pattern. This replaces schedule-dependent atomic additions. It adds temporary storage of numS * NumElementsPerSimplex² * sizeof(double) bytes (648 bytes per triangle for the flow’s nine-element system).

  • TextureSignalProcessing, SimpleTriangleMesh.inl: number connected-component roots in triangle order, then propagate labels in parallel. Atomic root numbering changed chart order, including the association of boundary perturbations with charts.

  • TextureSignalProcessing, TextureStitching.cpp: scatter the solved colors to the texture in node order. Different chart nodes can occupy the same pixel; parallel writes raced, whereas ordered writes consistently preserve the last node’s color.

  • TextureSignalProcessing, HierarchyConstruction.inl: assign supporting and covering triangles in triangle order. Last-writer atomic assignments otherwise chose different triangles and barycentric coordinates for the same atlas node.

  • TextureSignalProcessing, Operators.inl: collect boundary coefficients by chart instead of worker, so merging fixes the order of additions to shared matrix entries.

  • TextureSignalProcessing, QuadratureIntegration.h: statically schedule triangles whose integration sample lists are subsequently merged in worker order. This fixes accumulation order for a given worker count while preserving parallel integration.

These changes retain parallel geometry, element integration and solving. They do not enable the stitcher’s optional --jitter argument: --jitter 0 explicitly seeds from wall-clock time, and a fixed nonzero jitter seed would not repair the other causes. The stitcher’s internal degeneracy perturbations still use its process-local default random sequence. The repeatability target is identical inputs, helper binaries and thread configuration on the same platform, not bitwise equality across compilers or floating-point architectures.

textureConsolidationBuildsTextureFromRasters now runs the complete filter twice on the same gargoyle atlas and compares every output pixel. The existing camera, coverage and refusal checks remain in place.

Landing: these are working-tree changes in TextureConsolidation and its nested Misha, PhongRodriguesVF and TextureSignalProcessing submodules. Publish the dependency fixes first, then update their gitlinks in TextureConsolidation, publish that revision, and finally update MeshLab’s TextureConsolidation gitlink together with the regression check. No commits, pushes or gitlink changes are made by this investigation. The TextureSignalProcessing checkout also contains separate ongoing compile-time changes; review its combined diff before staging.

Open questions¶

These are about the algorithm’s intended conventions, so they go to you, and through you to the authors:

  1. Scale. What mesh scale do TextureFlow’s defaults assume? Should the adapter normalize — to a unit bounding-box diagonal, unit area, or something else — so that one set of defaults suits every layer?

  2. Defaults. The code and the paper disagree on four values (levels 6 vs 4, source smoothing 3e-4 vs 0.002, flow smoothness 0.5 vs 0.2, cutoff 0.05 vs 0.15). Which should MeshLab ship? Are the README’s values newer?

  3. Stability. The repository is three weeks old and changes daily. Do the authors intend the three-program interface to stay, or is a library API coming? That decides whether to pin now or wait.

  4. Preconditions. What exactly makes the stitcher fail with “Bad components”? A single connected component, a manifold mesh, non-overlapping charts, no zero-area UV triangles? The adapter should refuse each of these with a message rather than let a helper exit.

  5. Real photographs. The vase is real photographs. Should a separate default set, the paper’s RGB-D values, be offered for photographs rather than generated renderings?
