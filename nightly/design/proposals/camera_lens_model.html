Camera Lens Model¶

This document proposes lens distortion for raster cameras, so that photos calibrated with a real lens model (COLMAP, RealityScan, Metashape) can be used without undistorting them by hand, and so that the image-to-mesh alignment tools that follow have a camera they can refine. Stages 0 (removing vcglib’s distortion) and 1 (the lens) implemented 2026-11-02; Stage 2 (COLMAP import) not yet. The tables and the open questions were approved the same day. How the lens works today is in Data Model; this document keeps the plan and the record of how it was carried out.

See also: Data Model (rasters, planes, the .mlp file), Rendering, Orthographic Camera (the last change to CameraShot), Test Data.

Decisions¶

Taken 2026-11-02:

  1. A hard boundary between distorted and undistorted. A raster’s CameraShot is a pinhole camera, always, and everything that projects – filters, depth buffers, the GPU raster view – sees only that. The lens is a separate member of the raster that relates the pixels of the photo as shot (the file) to the pixels of the pinhole camera (the image in memory). It is applied in exactly two places: when a plane is decoded, and when a point picked on the photo as shot must be related to the camera (correspondences, imported keypoints). This is way A of the discussion of 2026-11-01; way B, a lens applied by every consumer, was rejected because the GPU path cannot apply it in a matrix and would need the undistorted image anyway.

  2. vcglib’s distortion is removed entirely, not kept beside the new model: the fields, the two conversion functions and the branches in Camera::Project and UnProject. vcg::Camera becomes a pure pinhole/orthographic camera.

Where things stand¶

Measured on 2026-11-02.

vcglib has a one-parameter radial model in vcg::Camera: std::array<S,4> k (only k[0] used) and DistorCenterPx. Camera::Project applies UndistortedToDistorted when k[0] != 0, on the camera plane in millimetres, against a centre converted to [-1, 1] coordinates – two different frames. The cubic solver (camera.ipp:393) forms Cardano’s discriminant as Q^3 + sqrt(R) where the formula has Q^3 + R^2, and takes one cube root of abs((int)(R - D)), marked MODIFICATO DA ME, which truncates its argument to an integer. DistortedToUndistorted is a first-order approximation, so the two are not inverses.

Nothing uses it. Of the 39 .mlp files in the repository, tests/local and .reference (every MeshLab sample project), none has a non-zero LensDistortion. The two vcglib importers that could fill it, import_out.h (Bundler) and import_nvm.h, set it to 0 on purpose (“To be uncommented when distortion is taken into account reliably”). MeshLab’s own .mlp writer writes "0 0". The only code that sets a non-zero k[0] is wrap/tsai/tsaimethods.cpp, a Tsai calibration wrapper that nothing compiles: old MeshLab’s three mutual-information plugins once included it, and the include and the call are commented out in all three (see Old MeshLab).

It is already inconsistent in MeshLab. CameraShot::project goes through vcg::Shot::Project, so a project with a non-zero LensDistortion would project with distortion on the CPU while the GPU raster view (projectionMatrix) and the interiors of the depth buffer’s triangles stay pinhole. No file triggers it today.

Who projects through a raster camera (project, unproject, projectionMatrix, viewRayThrough, buildDepthBuffer): filter_color_projection (7 calls), filter_img_patch_param (2), filter_camera (1), src/core/softdepthbuffer.h, and the raster view in src/render/renderwidget{,_raster,_render,_frame_plan}.cpp. Under the boundary none of them changes.

Who reads a raster image: everything goes through Document::ensureRasterPlaneImage (src/core/document_layers.cpp:813), the one lazy decode point, called from the document, the renderer and the color projection and texture consolidation filters. The layer panel’s thumbnails read the file directly with QImageReader and so show the photo as shot, which is right for a thumbnail.

The lens¶

A lens maps normalized camera coordinates, (x/z, y/z) of a point in front of the camera, from undistorted to distorted. The pinhole intrinsics stay in CameraShot and are the same on both sides:

file pixel    = K · distort(n)
working pixel = K · n

So the image in memory has the same size and the same K as the file; pixels that fall outside the photo after undistortion are transparent (alpha 0, which filter_img_patch_param’s alpha weight already honours). Being normalized, the lens is independent of resolution: Import Image to Current Raster rescaling the camera (RescaleViewportPx) leaves it alone.

Models. One rational Brown-Conrady model, OpenCV’s: radial k1..k6, tangential p1, p2. It covers COLMAP’s SIMPLE_RADIAL, RADIAL, OPENCV and FULL_OPENCV, and RealityScan’s and Metashape’s Brown export (Metashape’s b1 is an aspect change and goes into K; its skew b2 is not representable and is refused). The type carries a model enum so that an equidistant fisheye (OPENCV_FISHEYE, k1..k4) can be added when a dataset needs one.

Directions.

  • Distort(n): closed form. Undistorting an image needs only this one: for each working pixel, find the file pixel it comes from and sample it bilinearly.

  • Undistort(d): Newton iteration on Distort, from d, with a convergence flag; at most a few iterations for real lenses. Needed only for points picked or imported in the photo as shot.

Where it lives. A new vcglib header, vcg/math/lens_distortion.h, templated on the scalar, with a short sample in apps/sample/. It is general camera geometry with no MeshLab dependency, so it belongs in vcglib by the repository’s own rule; it composes with vcg::Camera rather than living inside it, so the pinhole camera stays what it is.

The only way a non-zero k reaches old MeshLab is passively, from a file it reads: LensDistortion in an .mlp (io_base/load_project.cpp:301, ReadShotFromQDomNode) or a shot pasted from the clipboard (glarea.cpp:2163), and k1..k4 of a PLY camera element through vcglib’s PLY importer. Behaviour does not change. The patch is prepared with Stage 0 and lands in old MeshLab before or with its next vcglib bump; until then its pinned vcglib keeps building.

Planes in memory and on disk¶

Every plane file of a raster is in the frame of the photo as shot, and is undistorted on decode. A plane made in memory – a snapshot, a mask or depth a filter writes – is in the working frame. When such a plane is saved, it is written as it is and the .mlp marks it undistorted="1", so that it is not undistorted twice on reload; old MeshLab ignores the attribute. The alternative, distorting it back on save, resamples twice for nothing. See Q3.

The .mlp extension¶

<VCGCamera ... LensDistortion="0 0"
           LensModel="brown" LensParams="k1 k2 p1 p2 k3 k4 k5 k6"/>

The parameter order is OpenCV’s, so that COLMAP’s and OpenCV’s numbers copy across unchanged. LensDistortion stays, as "0 0", because our reader and old MeshLab’s require it. Old MeshLab reads such a project as pinhole cameras on distorted photos, so it misprojects by the distortion. Nothing can prevent that short of not writing the project, and it is the same error it makes today on any undistorted-by-hand workflow done wrong.

Staging¶

Stage 0 – vcglib removal (table 1, M1, M2, M5, M10). Implemented 2026-11-02: -452/+31 lines in vcglib (285 of them wrap/tsai), -48/+18 in MeshLab. filter_layer’s copy of the camera parser warns about a non-zero LensDistortion as the core one does, until M3 merges the two in Stage 1. Verified: the full suite (only the known fileDialogsRememberWhereYouWere fails), all 62 vcglib sample targets, and a PLY camera written in binary and ASCII by the old and the new vcglib, byte for byte identical and read back the same. MeshLab’s .mlp writers already wrote "0 0" / "0.000000 0.000000", and still do. apps/test/camerashot (qmake only) fails to compile on two unrelated calls before and after. The 31-line patch for old MeshLab applies cleanly to its devel.

Found while verifying, not caused by this change: vcglib’s PLY camera does not round-trip the same way in binary and ASCII – a shot written both ways and read back projects one point to (530, 220) from the binary file and to (470, 180) from the ASCII one, with the old vcglib as with the new.

Stage 1 – the lens (vcglib header and sample, M3, M4, M6-M9, M11). Implemented 2026-11-02; what follows the planned tests below. Planned: about 150 lines in vcglib and 300 in MeshLab, of which M3’s merge removes about 80. Tests, in tests/test_document.cpp:

  • Distort / Undistort round trip under 1e-4 px over the whole image, for the 35 FULL_OPENCV cameras of the RealityScan export (k1 about 0.25, k3 up to 1.6: a strong lens, the hard case for Newton).

  • .mlp save and load keep the lens; a LensDistortion of "0 0" with no LensModel reads as the identity, a non-zero one warns.

  • End to end on the gargoyle fixture: distort its four photos with a known lens, give that lens to the cameras, load: the undistorted planes match the original photos (PSNR above 40 dB away from the transparent border), and Compute Face Scalar from Rasters reports the same counts as on the original fixture. This needs four more images in tests/sample_mesh/ (about 0.9 MB) or generating them in the test; generating is preferred.

  • Undo of a lens change restores the lens and the image.

As built: vcg/math/lens_distortion.h (156 lines) and the sample space_lens_distortion; in MeshLab +348/-380 lines of source, so the merge of M3 more than paid for the lens, and 249 lines of tests. The two .mlp camera parsers and two writers became one of each, CameraShot::readVcgCameraXml / writeVcgCameraXml; filter_layer’s copies and its private number parsers are gone, and so are the two pair parsers of document_internal.cpp. Where it departs from the plan:

  • No model enum. LensDistortion holds the eight Brown-Conrady parameters and nothing else; the enum is added with the fisheye model (Q4), when there is a second model to tell apart. The .mlp already names the model (LensModel="brown"), and refuses one it does not know rather than reading the photo as pinhole.

  • setRasterLens beside setRasterShot rather than M8’s setRasterCamera(shot, lens): the seven callers of setRasterShot stay as they are. Import Cameras to Visible Rasters calls both, inside the filter’s one undo step.

  • ensureRasterPlaneImage(raster, plane): it needs the raster’s camera and lens, so its 13 callers outside Document (renderer, four filters, two tests) pass the raster they already held. Import Image to Current Raster, which reads its file itself, undistorts it too.

  • Folds. A calibrated model can fold back on itself beyond the part of the image its photos constrained. Camera 21 of the RealityScan export (k3 -0.43) peaks at a normalized radius of 0.7046 while its photo’s corners reach 0.7079: 13 corner pixels (of every fourth) have no undistorted point, and Undistort reports them as not converged. Past a fold Distort lands inside the photo again, so IsInvertibleAt (the sign of the Jacobian, which Newton already computed) leaves such pixels transparent rather than repeating the photo mirrored. No working pixel of this dataset reaches a fold; the guard is for lenses that do.

  • The face-scalar check of the end-to-end test was dropped: Compute Face Scalar from Rasters reads cameras and depth only, never an image, so its counts cannot depend on the lens. The test checks the planes alone: PSNR 41.9-46.3 dB against the original photos over the four rasters, after two bilinear resamplings, with a pincushion lens (k1 0.12), whose undistorted corners are left transparent. The distorted photos are generated in the test.

  • Round trip measured on all 35 cameras rather than committed: the export is not under the dataset roots (.reference/TestDataset/2930Colmap). Over every fourth pixel the worst error is 8e-13 px; the test carries cameras 11 (the strongest, k3 1.78) and 21 (the fold) as literal values.

  • Checked against tools/colmap_to_mlp.py, written separately with the same conventions: three of the export’s photos decoded through their lenses match the script’s undistorted images to RMS 0.003 and at most 1 level per channel; the only difference is a half-pixel ring at the border, which MeshLab keeps (a border pixel reaches half a pixel past its centre) and the script drops. A 3840x2160 photo decodes through its lens in about 0.2 s, single threaded, on top of reading the file.

Stage 2 – COLMAP import. A reader for a COLMAP sparse model (cameras, images, points3D, text and binary) beside MeshLabProject*, producing the same raster entries, with the images found as tools/colmap_to_mlp.py finds them, points3D as a point cloud layer with colors, and every COLMAP model in Stage 1’s set imported natively. Open Project accepts cameras.txt / cameras.bin. About 300 lines. Tests: a small committed COLMAP text model of the gargoyle fixture (the four cameras with the Stage 1 lens, its points), and the RealityScan export as an optional dataset (MESHLAB2_REQUIRE_DATASET) checking the reprojection error of the points’ tracks under 1 px. tools/colmap_to_mlp.py is then removed; its --z-up turn is a transform of all layers and rasters, which Transform already does. See Q5.

Stage 3 – image-to-mesh alignment. A proposal of its own once Stages 1 and 2 are in: correspondence alignment (old edit_mutualcorrs, 3.2k lines, levmar) and mutual- information refinement (filter_mutualinfo, 2.6k; filter_mutualglobal, 4.6k). What this proposal fixes for it: picks are made on the displayed image, which is the working frame, and are mapped to the photo as shot with Distort when the lens is refined; the solver can be Eigen’s LevenbergMarquardt (in vcglib/eigenlib/unsupported), replacing levmar; and mutual information renders the mesh through the pinhole camera, which is exactly what it needs.

Open questions¶

  1. Old MeshLab and wrap/tsai. Old MeshLab must not break: audited under Old MeshLab – it never uses the fields, so a 31-line patch on its side keeps it building with unchanged behaviour. wrap/tsai is compiled by nobody, so removing it (V11) breaks nothing. Decided 2026-11-02: the fields are removed, and the patch goes to old MeshLab.

  2. Legacy LensDistortion. Decided 2026-11-02: read, ignored with a warning.

  3. Planes saved from memory. Decided 2026-11-02: written undistorted and marked undistorted="1".

  4. Fisheye. Decided 2026-11-02: later, when a dataset needs it; the enum leaves room.

  5. tools/colmap_to_mlp.py. Decided 2026-11-02: removed at the end of Stage 2.
