Folding the pymeshlab2 wheel into this repository¶

The Python wheel is built from a separate repository, cignoni/pymeshlab2, which carries MeshLab as a git submodule. This document proposes moving that build here and retiring the separate repository, and records the mapping table required by AGENTS.md before anything moves.

Status (2026-11-12): both tables approved; the in-app facade rename and steps 2–4 are done. pip wheel . builds pymeshlab2 from this tree, the wheel exposes the same 405 filters as the application, and wheels.yml builds and tests the wheels on devel (macOS arm64 and Windows x64, CPython 3.10–3.14; first green run 2026-11-03, 0ac8d6e8). Steps 5–6 (tag, archive) have not started: no release has been tagged yet.

See also: LLM Integration (why wheel/app convergence came up), Branches and Releases (the release machinery this would join), Python Scripting (the API the wheel exposes).

Why¶

Three reasons, in order of weight.

  1. The submodule pin is a standing staleness bug. The wheel repository pins MeshLab and that pin runs behind — 135 commits at the time of writing, so a locally built extension exposed 304 filters against 403 declared here. AGENTS.md already names this repository’s submodule hygiene as something the sibling repo suffers from; merging removes one of the two layers.

  2. The duplication is in CI, and it is large. wheels.yml re-implements the Qt install, the vcpkg bootstrap pinned to the manifest baseline, the overlay triplets and the vcpkg artifact caching that tests.yml, macos-dmg.yml and windows-portable.yml already perform, on the same two platforms the wheel targets. It already reaches back through the submodule for the triplets.

  3. The release machinery here already has the right shape. release.yml orchestrates three reusable workflows on a YYYY.MM tag, each of which supports workflow_dispatch, workflow_call and a devel push. A wheel job fits that pattern without inventing anything, and inherits the tag/version check — which would also give the wheel a real version, replacing the 0.0.1 it has never moved off.

Decisions taken¶

  • The distribution and the import name are both pymeshlab2, and the in-app facade follows (see The in-app facade). pymeshlab on PyPI belongs to the legacy PyMeshLab line (cnr-isti-vclab/PyMeshLab, latest 2025.7.post1, versioned YYYY.M[.postN]), which is still maintained. Publishing this API under that name as 2026.11 would sort as an ordinary upgrade, so an unpinned pip install -U pymeshlab would swap an incompatible API in silently, and the shared import name would stop the two from being installed side by side while scripts are ported. A calendar version cannot signal that break; a distinct name does. pymeshlab2 has never been published (PyPI returns 404), so nobody is broken by adopting it, and it follows the AGENTS.md rule that code identifiers follow the repository name.

  • cignoni/pymeshlab2 is archived, not deleted, and not until a tag-built wheel has gone green from here.

Step 3, in detail¶

The tests came over with three kinds of edit beyond their paths, all for the same reason: in this tree, a test that skips is a test that hides a failure.

  • pytest.importorskip("pymeshlab2") became a plain import. A broken or missing wheel used to turn the whole suite into skips and a green run.

  • Path guards went. test_mesh.py and test_smoke.py found the sample mesh through a working-directory-relative external/meshlab2/… path and skipped when it was absent, which in-tree it always would have been. They now resolve it from the test file; so do the two examples. “Filter missing → skip” guards went too: a missing filter is now a build defect, caught by the parity test.

  • Examples are loaded by file path, not imported as examples.<name>. Putting python/ on sys.path to make the package importable would also make import pymeshlab2 find the source package, which has no compiled module, ahead of the installed wheel.

test_single_mesh_filters.py was replaced, not moved. Its contract — every filter either runs or refuses — is the one tests/test_filter_smoke.cpp already owns, with a fixture ladder and an expected-refusals table. The Python copy ran one fixture and counted refusals as failures, so in-tree it failed 87 filters for saying, correctly, that a single triangle has no second layer or no rasters. What it could catch that ctest cannot, a plugin missing from the wheel, is now asserted directly: test_wheel_exposes_every_declared_filter requires the wheel’s filter ids to equal the ids in plugins/*/filters.json, both ways.

It still earned its keep on the way out. tests/data/simple.off is a single open triangle, an input the C++ ladder (which starts from a closed sphere) never gives, and on it, in the application as well as the wheel: subdivide_by_doo_sabin segfaults; remove_isolated_components_by_face_count refuses with “Missing component: PerFaceMark”, an internal error rather than an input requirement; and create_voronoi_scaffolding, sample_volume and remesh_to_quads_quadwild_bimdf do not finish within 60 seconds. These are filter bugs, and the guard belongs in the C++ smoke suite, not in a second sweep here. Since fixed (2026-11-03): FilterSmokeTests::survivesDegenerateInput runs every filter once on a single triangle, and the first four are fixed — the two samplers and Doo-Sabin in vcglib, which now refuse input they cannot handle instead of looping or reading unset corners. QuadWild remains, listed in that test’s slowOnDegenerateInput table: its automatic sizing divides by enclosed volume.

The in-app facade¶

Done 2026-11-03. The application’s console registers its own facade module (src/python/PythonHost.cpp:222–230, a types.ModuleType placed in sys.modules), and it was called pymeshlab; the user documentation taught import pymeshlab against it. If the wheel is pymeshlab2 and the console is pymeshlab, a script written in one does not run in the other — the portability the shared sources.cmake exists to give. So the facade is renamed too, with no alias, per the no-compatibility-names rule for the Python API.

Known wrinkles¶

  • Resolved in step 2: find_package(nanobind) sat inside the MESHLAB2_PYTHON_CONSOLE guard; it now runs for either option.

  • Resolved in step 2: the version comes from scikit-build-core’s scikit_build_core.metadata.regex provider reading MESHLAB2_VERSION out of CMakeLists.txt; the local build produced pymeshlab2-2026.11.

  • vcpkg’s python3 hijacks find_package(Python). Not foreseen by the table. The nanobind port depends on python3, and that port installs a vcpkg-cmake-wrapper.cmake which, whenever Development.Module is requested, points FindPython at vcpkg’s own 3.12 headers. The configure then fails against any other interpreter. The sibling never met it because its manifest lacked nanobind. Fix: nanobind moved into a python-console manifest feature, on by default (so the application, which embeds that very python3, is unchanged), and the wheel sets VCPKG_MANIFEST_NO_DEFAULT_FEATURES and takes nanobind from pip (build-system.requires, nanobind>=2.13; 3.1.0 built cleanly). Consequence for step 4: the wheel needs its own vcpkg install tree; it cannot reuse an application build’s.

  • The local wheel is tagged macosx_26_0, the build machine’s OS, because scikit-build-core reads MACOSX_DEPLOYMENT_TARGET from the environment and not from CMakeLists.txt’s 15.0 floor. CI must export MACOSX_DEPLOYMENT_TARGET=15.0.

  • An unrepaired macOS wheel does not import: _meshlab links @rpath/libgeogram.1.9.3.dylib and Qt frameworks that only scripts/repair_macos_wheel.py bundles. Row 10 was therefore moved in step 2, unchanged, to prove the wheel locally (QT_ROOT_DIR, VCPKG_INSTALLED_DIR, VCPKG_TARGET_TRIPLET and delocate needed).

  • ci/vcpkg-triplets/ has no x64-windows-release.cmake — both repositories name that triplet with the overlay set, and both fall through to vcpkg’s builtin. Consistent today, but it means the overlay is load-bearing only on macOS and Linux.

  • The test story becomes two-headed: ctest for C++, pytest for the wheel. Kept small on purpose: pytest covers only what is specific to the wheel (the binding surface, the examples, and that the filters a wheel exposes match the descriptors in this tree, the gap recorded in LLM Integration); filter behaviour stays in the three ctest tiers.

  • cibuildwheel’s isolated build environment must see the vcpkg install tree the way the existing workflows lay it out. This is the one mechanically unknown piece and should be proven on a branch before the sibling repo is archived. wheels.yml installs the tree outside the build directory (build-wheel-vcpkg), without default features, and hands it over through CMAKE_ARGS.

  • Measured in step 4: every interpreter builds into one build-wheel directory ([tool.cibuildwheel] config-settings). Locally, switching a built tree from CPython 3.12 to 3.13 recompiled only nanobind, _meshlab and MeshLab2Core — 23 seconds — where the sibling’s fresh directory per wheel rebuilt every plugin five times over. The cp312 wheel built that way passes python/tests too.

  • Texture Consolidation stays on in the wheels: turning it off would make the wheel’s filter set differ from the descriptors and fail test_wheel_exposes_every_declared_filter. Its three helper programs ship in the wheel under pymeshlab2/texture-consolidation/bin (9e386700), as they do in the DMG, ZIP and AppImage (db1dca4f), and CI caches them (0ac8d6e8), so the hour their stitcher takes to compile is paid only when the helpers change. wheel_smoke.py runs the filter, which is the only proof the vendored libraries load.

  • PyPI upload is not automated. The wheels go on the draft GitHub Release. The trusted-publisher route is described under Open items in Branches and Releases.

Order of operations¶

  1. Land the table (this document), approved. Done, together with the in-app facade rename, which touches nothing the wheel move does.

  2. In-tree build: rows 5–8, 11 (and 10, see Known wrinkles). Prove pip wheel . produces an importable pymeshlab2 locally. Done: the repaired cp313 wheel imports from a clean venv, lists 405 filters (identical to the application’s set), and passes the sibling’s wheel_smoke.py.

  3. Tests and examples: rows 12–23. Prove pytest green locally. Done: 12 tests pass with none skipped, against the repaired cp313 wheel; the moved wheel_smoke.py passes too. Run from the repository root with the wheel installed: python -m pytest.

  4. CI: row 9, plus a wheels job in release.yml. Prove green on devel. Written: wheels.yml (on devel pushes touching the bindings or packaging, by hand, and from release.yml, which attaches the wheels to the draft release). Proven: green on devel since 2026-11-03 (0ac8d6e8, 9e386700, 65d5212d, and by hand on 460c4d84).

  5. Tag a release; confirm the wheel builds from the tag.

  6. Only then archive cignoni/pymeshlab2.

Steps 2–5 are each independently revertible; step 6 is the point of no easy return.
