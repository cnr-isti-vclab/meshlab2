Folding the pymeshlab wheel into this repository¶

The Python wheel is built from a separate repository, cignoni/pymeshlab2, which carries MeshLab as a git submodule. This document proposes moving that build here and retiring the separate repository, and records the mapping table required by AGENTS.md before anything moves.

Nothing here has been done. The table below is for approval first.

See also: LLM Integration (why wheel/app convergence came up), Branches and Releases (the release machinery this would join), Python Scripting (the API the wheel exposes).

Why¶

Three reasons, in order of weight.

  1. The submodule pin is a standing staleness bug. The wheel repository pins MeshLab and that pin runs behind — 135 commits at the time of writing, so a locally built extension exposed 304 filters against 403 declared here. AGENTS.md already names this repository’s submodule hygiene as something the sibling repo suffers from; merging removes one of the two layers.

  2. The duplication is in CI, and it is large. wheels.yml re-implements the Qt install, the vcpkg bootstrap pinned to the manifest baseline, the overlay triplets and the vcpkg artifact caching that tests.yml, macos-dmg.yml and windows-portable.yml already perform, on the same two platforms the wheel targets. It already reaches back through the submodule for the triplets.

  3. The release machinery here already has the right shape. release.yml orchestrates three reusable workflows on a YYYY.MM tag, each of which supports workflow_dispatch, workflow_call and a devel push. A wheel job fits that pattern without inventing anything, and inherits the tag/version check — which would also give the wheel a real version, replacing the 0.0.1 it has never moved off.

Decisions taken¶

  • The published module becomes pymeshlab, matching the name AGENTS.md declares. The current pymeshlab2 name is retired at the same moment, so users take one breaking change rather than two.

  • cignoni/pymeshlab2 is archived, not deleted, and not until a tag-built wheel has gone green from here.

Known wrinkles¶

  • find_package(nanobind) sits inside the MESHLAB2_PYTHON_CONSOLE guard (CMakeLists.txt:165–170), and the wheel build sets that option OFF. The condition has to become if(MESHLAB2_PYTHON_CONSOLE OR MESHLAB2_PYTHON_WHEEL), or nanobind lookup moves out of the guard entirely.

  • Deriving the wheel version from MESHLAB2_VERSION needs a scikit-build-core metadata provider; the exact mechanism is unverified here and should be confirmed against the installed version before the table is executed.

  • ci/vcpkg-triplets/ has no x64-windows-release.cmake — both repositories name that triplet with the overlay set, and both fall through to vcpkg’s builtin. Consistent today, but it means the overlay is load-bearing only on macOS and Linux.

  • The test story becomes two-headed: ctest for C++, pytest for the wheel. That is a mild complication but also a gain — test_single_mesh_filters.py exercises the wheel path ctest structurally cannot reach, and post-move it becomes the natural place to assert that the filters a wheel exposes match the descriptors in this tree, the gap recorded in LLM Integration.

  • cibuildwheel’s isolated build environment must see the vcpkg install tree the way the existing workflows lay it out. This is the one mechanically unknown piece and should be proven on a branch before the sibling repo is archived.

Order of operations¶

  1. Land the table (this document), approved.

  2. In-tree build: rows 5–8, 11. Prove pip wheel . produces an importable pymeshlab locally.

  3. Tests and examples: rows 12–23. Prove pytest green locally.

  4. CI: row 9, plus a wheels job in release.yml. Prove green on devel.

  5. Tag a release; confirm the wheel builds from the tag.

  6. Only then archive cignoni/pymeshlab2.

Steps 2–5 are each independently revertible; step 6 is the point of no easy return.
